# Knowledge Layer

Status: v1 (Milestone 7). Work order: `2026-09-01() Project_Alexandria_OMP_Knowledge_Layer_Work_Order.md`.

## What it is

The knowledge layer attaches **What** to the globe's **Where + When**:

```text
Historical Polygon (feature NAME)
      │  click (runtime)
      ▼
History Atlas Entity  (ha:polity:*, data/entities.json)
      │  pre-resolved link
      ▼
Wikidata QID  (external identifier only — never a primary key)
      │  pre-fetched facts + sitelink
      ▼
Wikipedia summary  (REST v1, short extract only)
      │
      ▼
Knowledge Panel (right-side panel / mobile bottom sheet)
```

## Architecture

| Concern             | Where                                                                                                | Notes                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Polygon rendering   | `src/cesium/*`, `src/geojson/*`                                                                      | untouched by this milestone                                     |
| Entity model        | `src/knowledge/types.ts`                                                                             | `HistoryEntity`, `EntityKnowledge`, `KnowledgeRegistry`         |
| Entity ID scheme    | `src/knowledge/slug.ts`                                                                              | deterministic ASCII slug; isolated so the scheme can be swapped |
| Entity extraction   | `src/knowledge/entityRegistry.ts`, `scripts/extract-entities.ts`                                     | pure builder + script; writes `data/entities.json`              |
| Wikidata matching   | `src/knowledge/matchScore.ts` (pure), `src/knowledge/wikidata.ts` (API), `scripts/match-wikidata.ts` | build-time only                                                 |
| Manual overrides    | `src/knowledge/overrides.ts`, `data/entity-overrides.json`                                           | always beat automatic matching                                  |
| Knowledge pre-build | `scripts/build-knowledge.ts`                                                                         | writes `data/knowledge/entities-knowledge.json`                 |
| Wikipedia summaries | `src/knowledge/wikipedia.ts`                                                                         | REST v1 `page/summary`, 800-char cap                            |
| Runtime lookup      | `src/knowledge/knowledgeService.ts`                                                                  | static JSON fetch + in-memory cache, no external API at runtime |
| UI                  | `src/ui/knowledgePanel.ts`                                                                           | loading / matched / unmatched / error states                    |

## Entity Registry

Generated by `npx tsx scripts/extract-entities.ts` from all `data/world_*.geojson`
files (the polygon files themselves are never modified).

- One entity per normalized polity name; case/whitespace/diacritics variants
  merge (20 merges in the current dataset). Canonical name = most frequent
  original spelling; every original spelling is kept in `sourceFeatureNames`.
- `entity_id` format: `ha:polity:<ascii-slug>` (e.g. `ha:polity:roman_empire`).
  Deterministic; slug logic isolated in `slug.ts` for future migration.
- Extra dataset-derived fields: `firstYear`, `lastYear` (BC negative), `featureCount`.
- Current counts: 53 slices, 15,998 features, 5,835 unnamed features skipped,
  **3,004 entities**.

## Entity resolution (Wikidata mapping)

`npx tsx scripts/match-wikidata.ts` — build-time/pre-processing only.
A user click never triggers a Wikidata search (work order §B-5).

Signals (scoring: 0.5·name + 0.25·type + 0.25·temporal):

1. **Name/alias** — exact normalized label (1.0), alias match (0.9), prefix (0.5).
2. **Polity type** — candidate P31 checked against a cached subclass closure
   (P279\*) of `Q3024330` historical country, `Q6256` country, `Q7275` state,
   `Q1790360` empire (SPARQL, cached in `wikidata-type-closure.json`).
   Humans (Q5) score 0 and can never become confirmed/probable.
3. **Temporal plausibility** — P571 inception / P576 dissolution vs. the
   entity's dataset year span (±150 y tolerance).
   Resolution outcome (2026-09-01 run, 1 manual override + auto matching):

| status    | count                       |
| --------- | --------------------------- |
| confirmed | 428 (427 auto + 1 override) |
| probable  | 898                         |
| ambiguous | 618                         |
| unmatched | 1,060                       |

1,326 entities have pre-built knowledge entries; 1,146 of them carry an
English Wikipedia summary.

Status thresholds:

| status      | rule                                                                                    |
| ----------- | --------------------------------------------------------------------------------------- |
| `confirmed` | score ≥ 0.90 **and** exact label **and** polity-type ≥ 0.6 **and** temporal neutral+    |
| `probable`  | score ≥ 0.65 and any type signal (weaker matches stay reviewable, never auto-confirmed) |
| `ambiguous` | two candidates within 0.05 — both kept in `candidates`, nothing decided                 |
| `unmatched` | everything else                                                                         |

All fields (`match_status`, `match_confidence`, `match_method`, `candidates`)
persist in the registry for audit.

**Manual overrides** (`data/entity-overrides.json`):

```json
{
  "ha:polity:joseon": {
    "wikidata_id": "Q28179",
    "status": "confirmed",
    "note": "optional reason"
  }
}
```

Overrides always win over automatic matching; malformed QIDs are reported and skipped.

### Determinism, caching, failure behavior

- Every raw API response is cached under `data/knowledge/wikidata-*.cache.json`;
  re-runs only hit the network for cache misses, so results are deterministic
  and rate-limit friendly (sequential requests, ~100–250 ms delays, ≤50 ids
  per `wbgetentities` batch, descriptive User-Agent per Wikimedia policy).
- A failed request skips the affected entity for that run and preserves its
  previous registry value — API errors never destroy existing data.

## Knowledge pre-build

`npx tsx scripts/build-knowledge.ts` fetches, for every confirmed/probable
entity: label, description, aliases, inception (P571), dissolution (P576),
capital (P36), predecessor (P155), successor (P1366) — `null` when Wikidata
has no value; facts are never invented — plus the English Wikipedia summary
via sitelink. Output `data/knowledge/entities-knowledge.json` is a
`KnowledgeRegistry` keyed by `entity_id` with fetch-time provenance.

Wikipedia usage is a short extract (≤800 chars) + canonical URL + optional
thumbnail; full articles are never ingested or stored.

## Runtime & UI

- `knowledgeService.ts` fetches the two static JSON files once per page load
  (in-memory promise cache) and resolves feature NAME → entity → knowledge.
- `knowledgePanel.ts` renders on polygon click:
  - **matched**: thumbnail, name, period, description, capital, predecessor,
    successor, aliases; hidden when the underlying field is null.
  - **unmatched** (no entity / no link): _"No linked historical reference yet."_
  - **loading**: _"Loading historical information…"_
  - **error** (static JSON missing): _"Historical information is temporarily
    unavailable."_ — the globe is unaffected; failures never propagate.
- Attribution footer: _Data: Wikidata · Text: Wikipedia_ + QID link, plus a
  _Read more_ link to the Wikipedia article. Wikipedia text is never presented
  as History Atlas' own content.
- Desktop: fixed right-side panel; ≤768px: bottom sheet.

## Locale policy

English-first. `WikipediaKnowledge.language` and the per-language sitelink
lookup are structured so a locale switch (user locale → English → fallback)
can be added later without schema changes.

## Deployment notes

`vite.config.ts` copies `data/entities.json` and
`data/knowledge/entities-knowledge.json` into `dist/data/`. The build fails
fast if the knowledge JSON is absent — run the two build scripts after
changing the dataset:

```bash
npx tsx scripts/extract-entities.ts   # regenerate the registry
npx tsx scripts/match-wikidata.ts     # resolve QIDs (cached, resumable)
npx tsx scripts/build-knowledge.ts    # pre-build knowledge JSON
```

## Known limitations / future extension points

- Name-derived slugs can in principle collide; merges stay auditable via
  `sourceFeatureNames`. A numeric ID migration point exists in `slug.ts`.
- Temporal matching uses whole-year precision; Wikidata precision is often
  year or coarser.
- No reverse verification: a matched QID is scored, not human-verified. The
  override file is the correction path; `ambiguous` and `unmatched` entities
  are the review queue.
- Future work orders (per work order §15): event layer, relations, temporal
  edges — the registry/knowledge split is designed to carry those without
  schema breaks.
